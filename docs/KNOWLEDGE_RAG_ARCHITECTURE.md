# 企业知识库与 RAG 方案

## 目标

知识库按“招投标项目”保存一份招标文件和一份对应标书。招标文件负责提供需求、评分点和资格要求，对应标书负责提供响应方案和可复用内容。MySQL 保存可追溯业务数据，Qdrant 保存可重建的稠密向量，应用层用章节、关键词和向量相结合的混合检索。

## 数据分工

| 数据 | 存储 | 用途 |
| --- | --- | --- |
| 项目、账号、文件、状态 | MySQL | 权限隔离、项目视图、重试和审计 |
| 原文、章节切片、标题层级 | MySQL `knowledge_item` / `knowledge_chunk` | 详情查看、关键词检索、关系映射 |
| 图片、OCR、结构化字段 | MySQL `knowledge_asset` | 图片库、证件字段、素材匹配 |
| 向量和检索载荷 | Qdrant | 语义召回；索引损坏时可从 MySQL 重建 |
| 模型 | Ollama | 本地生成 BGE-M3 文本向量；不依赖云端 API |

MySQL 是事实来源，Qdrant 不是业务主库。删除或重建 Qdrant 不会删除项目、正文和素材，只需重新执行向量索引。

## Word 入库流程

1. 上传接口以 1 MB 分块从 multipart 临时文件写入租户目录，避免将数百 MB 的 DOCX 再复制成同尺寸内存对象；前端显示真实的文件传输进度。创建项目和两份文件记录后返回项目 ID。客户端仍需传完原始文件，网络传输时间取决于文件大小和连接速度。
2. DOCX 是 ZIP/OOXML 容器，不能仅凭扩展名认定它只有文字。本机三份历史标书分别约 354 MB、471 MB 和 612 MB，媒体文件占了大量体积。基础解析直接读取 `word/document.xml` 与 `word/styles.xml`，不再用 `python-docx` 加载完整包，也不解压图片；图片数量从 ZIP 目录统计，图片字节和 OCR 留给后台。
3. 基础解析按 Word 正文 XML 的原始顺序读取段落、标题和表格，保留表格行列文本。先用 Heading 样式、继承样式和有效 `outlineLvl` 建立章节树，再用编号规则补充标题；`outlineLvl=9` 这类非标题样式不会升级成章节。每个切片携带完整章节路径，例如“章节：第三章 > 3.2 配送方案”。
4. 每个章节按约 1000 字切片，重叠约 120 字，正文和表格保持同一章节上下文。
5. 正文、章节切片和处理状态先写入 MySQL；不等待 OCR 或向量生成即可查看和关键词检索。解析日志记录正文字符数、章节数和媒体数量，便于实测不同文件。
6. DOCX 的图片数量先从 ZIP 目录快速统计。图片字节解压、图片文件写入、感知哈希去重和 OCR 不阻塞基础正文；后台从 Word relationship 解析图片与附近章节/表格文本，再补图片素材、OCR、证件分类和结构化字段。
7. Qdrant 向量写入由后台任务执行。两份文件的 MySQL 切片完成后，先以关键词候选生成可查看的初步需求—响应关系；Ollama/Qdrant 完成后再用语义分数精排。Ollama 暂时不可用不会把已经完成的 Word 解析标成失败。
8. 项目 Word 格式模板提取排在正文和切片处理之后运行，避免数百 MB 文件的 ZIP 重写与正文解析争用磁盘。

本机对三份真实标书执行了只读抽取与切片计时（不含上传传输、数据库写入、OCR 和向量化）：

| DOCX 大小 | 正文字数 | 章节数 | 切片数 | 媒体项 | 结构解析与切片耗时 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 354 MB | 159,816 | 935 | 995 | 1,045 | 1.77 秒 |
| 471 MB | 155,838 | 956 | 1,015 | 1,443 | 1.92 秒 |
| 612 MB | 141,172 | 733 | 784 | 1,344 | 1.68 秒 |

这是解析阶段的本机基准，不代表用户上传总耗时；大文件的网络传输与后台图片 OCR 仍会更久。后台章节上下文也直接从正文 XML 和 `document.xml.rels` 关联图片，不加载 DOCX 的全部媒体部件。

## 混合检索

检索请求包含完整章节语义和业务关键词。应用层先执行：

- MySQL 元数据和权限过滤；
- Qdrant BGE-M3 语义召回；
- MySQL ngram FULLTEXT 关键词召回；
- RRF/加权融合；
- 章节标题和业务关键词加权；
- 素材细分类、有效期、明暗标和篇幅维度排序。

项目内需求-方案映射使用批量向量查询，按每个招标章节独立计算候选，不共享一个全局 query。初步映射先基于 MySQL 关键词倒排表运行；向量索引完成后以 BGE-M3 相似度和章节标题重合度融合，更新匹配分数。没有向量结果时保留 MySQL 关键词候选，因此 Ollama 停止时仍可查看基础对应关系。

## 专业 RAG 处理链路

现有实现已具备“结构解析 → 章节树 → 章节切片 → 双路召回 → 融合排序 → 需求方案映射”的基础链路，不把整份标书交给模型一次性总结，也不按固定页数切割 Word：

1. **解析层**：读取 OOXML 的正文段落、Heading/大纲级别、编号、表格行与来源文件；正文里的目录字段仅作为参考，优先使用实际正文标题建立目录树。文档结构无法确定时保留“文档内容”路径，不臆造章节。
2. **切片层**：以章节为边界，约 1,000 字切片、约 120 字重叠；每段附带项目 ID、文件角色（招标/投标）、章节路径、来源文件和块类型。评分点、资格条件、废标条款等短条款应作为独立块保留，避免与邻近段落合并后失去可追溯性。
3. **存储层**：MySQL 是原文、章节、结构化需求、切片和任务状态的事实来源；Qdrant 只保存可重建向量和过滤载荷。切片先事务写入 MySQL，再异步写入向量库，向量失败可重试/重建，不能反向阻断正文可用性。
4. **检索层**：先按公司、项目/文件角色、状态和类别过滤；MySQL ngram 全文检索召回精确术语，Qdrant + BGE-M3 召回语义相近内容；用 RRF 融合，并对章节标题、业务关键词、条款类型和来源角色做轻量加权。候选不足时保留关键词降级结果；图片素材只在文本候选完成融合并截取 Top-K 后补查，避免对整个扩召候选集逐条加载图片。命中图片语义切片时，从其注释标题中的素材 ID 精确回挂图片，避免返回同一文件内无关图片。
5. **当前需求—方案对应**：目前以招标文件切片为待匹配项，每条切片独立检索对应标书切片；候选只来自该项目的标书文件。项目匹配在有向量分时使用关键词 0.55、语义 0.45 的融合分，并按章节标题重合轻量加权；纯语义候选需先过较高相似度门槛。结果保留需求、响应、来源章节和分数，分数代表相关性，不等于人工确认的正确性。

下一阶段建议：

1. 从招标切片中抽取并标注评分点、资格要求、废标条款、服务要求等需求类型，映射记录继续保存来源切片 ID；用户确认后再标记为已核验，避免把一般说明段落都当成必须响应项。
2. 正文生成时只把排序后的有限证据片段交给生成模型，并绑定来源切片 ID；证据缺失时返回待补充/无匹配，不把向量相似度当作事实正确性的证明。
3. 先积累人工标注的“需求—正确响应”样本，再评估是否需要本地 reranker；在此之前不增加模型调用或显存开销。

性能原则：上传请求只负责文件落盘和建立项目；解析不运行逐页 OCR、不解压所有图片、不调用大模型。章节抽取与 MySQL 切片完成后立刻可用，图片 OCR、embedding 和语义精排异步执行。文件传输本身仍受 354–612 MB 原文件大小与本机磁盘/网络速度限制。

## Qdrant 载荷

每个向量点包含 `company_id`、`item_id`、`project_id`、`category_id`、`doc_role`、`chunk_kind`、`section_title`、`section_path`、`page_number`、`source_name` 和正文片段。项目、文件角色和章节路径以 MySQL 切片行中持久化的元数据为准；只有历史切片缺少字段时才从项目关联关系回退推导。`company_id` 作为强制过滤条件，避免不同公司的素材互相召回。项目、文件、类别等字段在服务版 Qdrant 使用 payload index 加速过滤。

## 单机部署边界与后续演进

当前实现面向单机试用：MySQL 保存权威业务数据，单机 Qdrant 持久化向量，Ollama 本地运行 `bge-m3`。切片先落 MySQL，再异步写 Qdrant；MySQL 中的 `knowledge_rag_task` 保存待处理、处理中、完成或失败状态、尝试次数和租约。后端启动后会遍历启用状态的公司，在各自租户上下文中恢复遗留的处理中任务并投递待处理任务；恢复只访问已存在的公司数据库，不会为了扫描而创建空租户库。Qdrant 未就绪时跳过恢复，不阻塞正文解析和服务启动。素材与项目详情会返回向量索引状态、成功索引切片数和失败原因，诊断接口会汇总索引任务、素材状态以及 MySQL ngram 全文索引是否可用。

向量写入以 MySQL 切片 ID 作为稳定业务 ID，并结合公司 ID 生成 Qdrant 点 ID；重试使用 upsert，因此允许至少一次投递而不会重复生成点。后台任务按 `RAG_VECTOR_TASK_MAX_ATTEMPTS` 和 `RAG_VECTOR_TASK_RETRY_BASE_SECONDS` 执行有限指数退避，达到上限后保留失败状态；修复 Ollama/Qdrant 后可通过向量重建接口重新补齐。单机 Qdrant 本地文件模式应由单个后端进程独占，不作为多副本共享存储。若部署为多进程/多副本，还需增加独立 worker、租约心跳和死信队列，并改用服务版 Qdrant。

下一阶段扩展顺序：

1. 建立可标注的评测集：招标章节、对应响应章节、应召回切片、证件图片类别；持续统计 Recall@K、MRR、误匹配率和人工接受率。
2. 基于评测集调节章节切片长度、关键词/向量融合权重、匹配置信度阈值，避免只按主观体验调整。
3. 需要多个后端进程或多台服务器时，将当前单进程任务派发升级为独立 worker，增加心跳租约、可配置退避重试和死信处理；同时将 Qdrant 切换为服务部署，配置快照/备份与集合版本。
4. 只有在评测证明仍有明显排序误差后，再加入本地 reranker；当前先用 MySQL 关键词 + BGE-M3 + 章节路径融合，保持显存与延迟适合 RTX 2070 Super。

目前后台图片任务仍会扫描文档中识别出的全部图片，图片 OCR 仍可能持续较久，但它与正文切片、初步需求方案映射已分离。后续可按章节关键词、图片尺寸/版式和证件特征将图片分为高优先级和普通素材，限速识别并提供可恢复进度。

## 运行前检查

```powershell
# 启动 Ollama，并确认向量模型存在
ollama serve
ollama pull bge-m3
ollama list

# 启动后端
cd "C:\path\to\bid-document-agent\backend"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 3896
```

后端 `.env` 使用 MySQL、Qdrant 和 Ollama 配置。首次切换新的 embedding 模型或维度时，使用新的 `QDRANT_COLLECTION_KNOWLEDGE` 名称，再执行：

```powershell
$r = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:3896/api/knowledge/vector/reindex
$r.data | ConvertTo-Json -Depth 5
```

重建结果中的 `knowledge_chunks_failed` 应为 0。Ollama 未启动时，基础 Word 解析和 MySQL 关键词检索仍可使用；补开 Ollama 后再次重建即可补齐 Qdrant。

## 调优参数

- `OLLAMA_EMBEDDING_BATCH_SIZE`：本机显存不足时降到 4 或 8；2070 Super 建议从 8 开始。
- `QDRANT_WRITE_RETRIES`：本地单机建议 2 到 3。
- `RAG_VECTOR_TASK_MAX_ATTEMPTS` 与 `RAG_VECTOR_TASK_RETRY_BASE_SECONDS`：控制后台向量写入的有限退避重试，默认 3 次、基准间隔 2 秒。
- 切片长度：默认约 1000 字，法律条款密集的招标文件可降到 700 到 900；方案叙述较长时可提高到 1200。
- 重叠长度：默认约 120 字，主要用于避免评分点跨切片丢失。
- 项目映射最低分：当前保留低分过滤，同时保留“待确认”状态，不把低证据内容默认为准确响应。

## 失败处理原则

Word 正文、章节切片和 MySQL 状态写入失败，才会将对应文件标为“解析失败”；Qdrant 或 Ollama 写入失败只标记向量索引不完整。项目页会分别显示招标文件和对应标书的失败原因，并提供单文件重新解析按钮。重试会复用原始文件，不删除项目关系。
