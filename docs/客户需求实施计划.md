# 客户需求实施计划

## 需求现状

| 客户需求 | 当前系统已有能力 | 本轮结果与待办 |
| --- | --- | --- |
| 多家公司使用、账号管理 | 已有公司/账号/角色/管理员入口；SQLite 与 MySQL 后端均有实现，业务库按公司隔离 | `MULTI_COMPANY_ACCOUNTS.md` 已补充 SQLite/MySQL 数据落点、迁移步骤和文件备份边界。仍需在目标 MySQL 实例完成双公司隔离、停用/恢复和备份恢复验收。 |
| 车辆网点路线图 | 原系统没有路线规划模块 | 本轮完成首版并增加示例集团业务流程：维护自有送菜网点，录入本次招标学校/单位，自动完成最近网点归属、配送顺序规划、高德道路路线计算和路线图 PNG 下载。 |
| 竞标对手资金数据调研 | 尚无专门调研流程 | 后续做成有来源的公开信息研究工具；必须显示来源、发布日期、指标口径和抓取时间，不将估算包装成事实。先确认行业、竞对范围、所需财务指标及允许的数据来源。 |
| 发票核验截图批量处理 | 已有单张发票 OCR、字段修正、本地校验和税务平台查验协助流程 | 后续扩为多文件批次：逐张识别、异常项人工确认、批量导出结果；税务平台仍按其验证码/登录/频率规则人工完成或逐张确认，不承诺未经授权的自动化绕过。 |

## 路线图首版范围

1. 首页增加「车辆网点路线图」入口。
2. 用户录入城市、配送中心、1–14 个配送网点，选择是否返回配送中心；地址按填写顺序经过。
3. 后端用高德地理编码和驾车路线 Web 服务获得坐标、路线、里程、耗时和逐段指引。
4. 前端通过高德 JS API 显示地图、起终点及网点标记、路线线条。
5. 高德服务 Key 只放后端 `AMAP_WEB_SERVICE_KEY`；浏览器端使用高德 JS Key `VITE_AMAP_JS_KEY` 与安全密钥 `VITE_AMAP_SECURITY_CODE`。缺少配置时页面显示清楚的配置提示。

示例集团路线图页面补充：自有配送网点保存在当前公司业务库；本次招标的学校/单位只作为当前规划需求点；系统按地理距离将需求点归属到最近自有网点，并按最近邻策略生成访问顺序；结果可下载为带标题、点位、里程和预计时间的 PNG 图片，作为图文标书插图素材。

首版按用户输入顺序规划，不做多车辆拆单、载重/时窗约束、全局最短路径优化、路线保存、实时交通刷新或历史线路管理。路线和地址会发送至高德服务进行解析与规划。高德账户需要开通相应 Web 服务和 JS API 权限，并遵守其配额与使用条款。

### 本机配置与联调

1. 在高德开放平台创建 Web 服务 Key 和 Web 端（JS API）Key，并为浏览器 Key 配置安全密钥及允许访问的域名/来源。
2. 在 `backend/.env` 设置 `AMAP_WEB_SERVICE_KEY`；在 `frontend/.env.local` 设置 `VITE_AMAP_JS_KEY` 和 `VITE_AMAP_SECURITY_CODE`。不要把 Web 服务 Key 写入前端配置或提交到代码仓库。
3. 重启后端和 Vite 前端，使环境变量生效。首页进入「车辆网点路线图」，填城市、配送中心和网点后点击「规划驾车路线」。
4. 分别验证：不返回配送中心、返回配送中心、多网点顺序、无效地址、缺少后端 Key、缺少浏览器 JS Key。前者应仍可显示路线结果，后几项应给出对应错误或配置说明。

本工作区没有配置可用于端到端请求的高德 Key，因此已完成代码构建检查，真实地址解析、配额和地图展示仍需在配置 Key 后验证。

## 建议实施顺序

### 阶段 1：账号和租户验收

- 用管理员创建两家测试公司及各自账号，确认普通账号不能读取对方项目、知识库、上传文件、发票结果和路线记录。
- 在目标 MySQL 配置上验证认证库与公司业务库映射；记录公司创建、停用、恢复及首次访问的行为。
- 做一次 MySQL 和上传目录备份恢复演练，并按 `MULTI_COMPANY_ACCOUNTS.md` 的 MySQL/SQLite 模式说明操作。
- 再决定各公司是否需要独立高德 Key、模型 Key 或套餐配额；现有路线接口使用部署级高德服务 Key。

### 阶段 2：车辆网点路线图完善

- 当前首版联调高德 Key，验证城区地址、同名地址、地址解析失败、网点上限和地图展示。
- 收集路线规划规则：网点是否可自动排序、是否必须回仓、是否存在多辆车、车辆载重/容积、配送时间窗、冷链要求、避开道路等。
- 有规则后再做路线优化与保存；如要为同一客户跨会话保存路线，新增租户隔离的路线和网点数据模型。

### 阶段 3：发票批量核验

- 支持多张图片/PDF上传和独立 OCR 结果，显示每张发票的识别状态、字段完整性和异常原因。
- 提供人工修正、重试、批次汇总及 Excel/CSV 报告；原始图像和 OCR 结果按公司隔离并设定保留策略。
- 税务平台查询作为单独步骤，保留人工确认和失败重试；先调研官方可用接口及使用规则，再确定自动化程度。

### 阶段 4：竞对资金数据调研

- 先确定研究对象识别方式（公司名称/统一社会信用代码）、业务区域、时间范围和指标口径。
- 建立可审计的来源清单，优先接入合法公开的数据源；每条结论保留来源链接、原文摘录、发布时间和采集时间。
- 区分公开财报事实、招投标历史金额、工商信息与模型推断，输出置信度和缺失项；不推测非公开账户或未经证实的资金数据。
- MVP 先做查询工作台和带引用的报告导出，再评估数据源授权、费用、更新频率和企业级并发。

## 上线验收清单

- 高德后端 Web 服务 Key 与浏览器 JS Key 分开配置，不在前端暴露 Web 服务 Key。
- 用户未登录不能调用租户业务接口；管理员接口仅管理员可访问。
- 两家公司分别登录后，业务记录和上传文件不串租户。
- 路线地址在发送到高德前由用户明确提交；失败时展示可操作错误，不保存或记录 Key。
- 发票批次报告和未来的竞对报告都可追溯到来源，且明确展示不确定信息。
